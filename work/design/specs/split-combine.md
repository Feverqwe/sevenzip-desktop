# Разделение и объединение файлов

Актуализация макета v64. Отдельные команды и формы исключены. Многотомные архивы сохраняются.
Описания прежних поверхностей ниже сохранены для справки. См. [план интерфейса](implementation-scope.md).

Статус: автономная проработка 5 ноября 2026. Обе формы используют общие источник,
SystemPathField, поля, раскрытие, сообщение и постоянную строку действий.
HTML показывает примеры native-результатов; не разбирает настоящую файловую
систему, размеры или последовательность частей.

## Вызов и контекст

Команды находятся в «Файл → Дополнительно», без постоянных кнопок на toolbar.
Для Split нужен один обычный файл доступного filesystem provider; папка,
множественный выбор и архивная запись не подходят текущему маршруту. Для
архивной записи сначала используется обычное сохранение отдельной копии.
Read-only источник не означает автоматически запрет чтения: возможность даёт
provider, а назначение должно быть доступно для записи.

Combine начинается с одной первой части, а не произвольного выделенного набора.
Источники, место и выбор захватываются при вызове; смена панели не изменяет
запрос. Имя первой части разбирает native CVolSeqName, не регулярное выражение
в кнопке. Пример `.001` не ограничивает поддержанные владельцем последовательности.

Начальное назначение — другая обычная доступная для записи панель, если она
видна, иначе текущая папка. Выбор папки системный; отмена выбора сохраняет
параметры и возвращает фокус. Неподдержанный источник объясняется в форме,
подтверждение недоступно. Cancel возвращает прежнее выделение и фокус списка.

## Разделить файл

Источник с именем и полным местом, папка для частей, редактируемый размер части.
Ни сжатия, ни настроек архива, ни пароля вывода. Подписи: «Размер части»,
«Например, 100M или 1G». История/актуальные варианты не требуют списка устаревших
носителей CD/DVD. Значения всё равно принимает действующий native parser.

Сохраняется возможность нескольких размеров через пробел: последний повторяется.
UI не вычисляет размеры независимым парсером и не теряет исходный текст при
ошибке. Пустой/нулевой/неверный/слишком большой для типа размер отклоняется
родным владельцем. Размер первой части должен быть меньше исходного файла;
пустой файл по этому правилу не разделяется.

Ошибка показывается рядом с источником и полями в той же форме, без второго
окна поверх ввода. Значение сохраняется для исправления, проблема связана с
полем через accessibility. Старый пункт каталога split-error теперь показывает
эту же форму с ошибкой, не вторую независимую реализацию.

Кратко показываем схему имён: `имя.001`, `имя.002` и далее. Реальные имена,
ширина числового суффикса и количество определяются native планом. На этапе
подготовки большое количество частей требует отдельного решения с фактическим
числом, «Отмена» и «Разделить». Initial focus — Cancel. Порог остаётся у
действующего владельца; макет не дублирует его. Число 500 — демонстрационный
вердикт preflight, не расчёт из текстового поля в JavaScript.

Исходный файл сохраняется. Занятое имя любой планируемой части останавливает
запуск/публикацию с конкретным именем; предлагаем другую папку. Нет Replace,
Keep Both и автоматического переименования отдельных частей — это разрушило
бы последовательность и не поддерживается текущей транзакцией записи.

## Объединить части

Источник — первая часть и папка исходников. Редактируются папка и отдельное
имя результата. Начальное имя берём из native GetCombinedName, а не удаляем
последние четыре символа имени. В раскрытии «Найденные части» показаны полные
имена в порядке native последовательности. Ручной drag reorder отсутствует.

Неверная первая часть, одна найденная часть или отсутствие данных объясняются
до запуска. Если после пропуска есть более поздние части той же последовательности,
сообщаем недостающую и блокируем объединение префикса. Нужно добавить недостающую
часть и повторно подготовить план. Эта проверка требует расширить preflight,
используя существующий CVolSeqName, поскольку текущий LoadParts останавливается
на первом отсутствующем имени и сам не замечает последующее продолжение.

Непрерывная найденная последовательность не доказывает наличие последней части:
общий формат сырых частей не хранит ожидаемое полное количество. Поэтому
пишем «Найденные», просим держать все части в одной папке, не показываем
необоснованное «Все части на месте». Не вводим новый контейнер/манифест ради
такого обещания. Объединение копирует байты в исходном порядке, не проверяет
содержимое архива и не заменяет отдельную проверку контрольной суммы.

Существующий результат, совпадение с одной из частей или недопустимое имя
не дают запустить запись поверх исходника. Предлагаем изменить имя/папку.
Существующее имя не открывает общий диалог Replace и не очищается заранее.
Редактируемое имя результата — адаптация текущей формы: native план уже имеет
OutputPath, но нынешний CApp создаёт его из фиксированного GetCombinedName.
Проверка пользовательского basename и пути остаётся у владельца файловой операции.

## Операция и исходы

Обе команды запускают отдельное немодальное окно: источник, назначение, один
индикатор, свернуть/остановить. Нет времени, скоростей, счётчиков и конфликтов
файлов из копирования. Пауза предлагается только по возможностям реального
транспорта; макет её не обещает. Пароль не нужен для чтения сырых байтов частей.

Успех означает завершение native записи и публикации, после чего окно закрывается
автоматически с кратким статусом. Ошибка/отмена остаются видимыми с причиной
и фактическим результатом. Изменившийся источник, исчезнувшая/нечитаемая часть,
ошибка записи или конфликт, возникший после preflight, не превращаются в успех.
Исходники не удаляются и не изменяются этими командами.

Используется существующая staging-транзакция без перезаписи: создаются служебные
выходы, затем публикуются готовые имена. При отказе выполняется её cleanup/rollback.
Не обещаем безусловную атомарность всего набора на любом носителе. Неудача очистки
или частичная публикация должна быть отражена как фактический остаток, а не
скрыта общим «всё отменено». Удалять разрешено только подтверждённо свои объекты;
замена опубликованного файла другим процессом не должна направить rollback на
чужой файл. Это требование к усилению владельца транзакции, не готовая гарантия UI.

Текущий InputSnapshot сравнивает вид/ссылку и размер, не все изменения содержимого.
Поэтому не обещаем, что native обнаружит любую запись с сохранённым размером.
Сильная проверка идентичности/стабильности и отчёт остатков требуют отдельной
адаптации существующего владельца. Перед началом повторно проверяются исходники,
план и назначение; native no-overwrite защита действует и после этой проверки.

[прогресс](../../../src/fileops/volumes/qtvolumeprogress.h).
Оригинальные SplitDialog.rc, SplitUtils.cpp и определения CVolSeqName/GetNextName
прочитаны из локального исходного архива. Нового импорта или C++ изменений нет.

Сохраняем native parser, порядок, число/имена, чтение/запись и обработку ошибок.
UI передаёт типизированные планы существующему IQtVolumeServices/VolumeOperation,
не запускает console-клиент и не повторяет бинарные циклы в форме. Application-owned
операция не должна зависеть от времени жизни закрытой панели.

До реализации нужно подключить: захват выбранного источника/назначения, inline
ошибки, отдельное имя Combine, preflight пропусков, capabilities/состояния общей
операции, безопасную идентичность и итог rollback там, где текущая граница слабее.

Проверки: Split→Combine даёт исходные байты; Unicode/пробелы; несколько размеров
и повтор последнего; ноль/переполнение/размер не меньше файла; подтверждение
множества частей/Cancel; имена с разной шириной суффикса; не первая/одна часть;
пропуск с последующим продолжением и неизвестная последняя; нулевой общий объём;
занятое/равное исходнику назначение и гонка; исчезновение/изменение/ошибка чтения;
cancel/write/publish/cleanup failure с проверкой исходников и оставшихся выходов;
выбор папки/Cancel, фокус, компактные/длинные значения. HTML проверяет только
демонстрационные состояния, связывание формы и компоновку.
